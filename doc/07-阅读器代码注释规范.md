# 阅读器代码注释规范

## 目的
本规范用于约束小说/漫画阅读器相关代码的注释质量，覆盖后端 `RuoYi-Vue-Plus`、管理端 `plus-ui`、以及 `reader-uniapp` 小程序/H5 工程。

从 2026-08-14 起，凡是阅读器需求新增或修改的代码，都必须同步补齐注释，不允许把“后面再补注释”作为默认做法。

## 适用范围
- 后端：`ruoyi-modules/ruoyi-reader/**`
- 管理端：`plus-ui/src/api/reader/**`、`plus-ui/src/views/reader-admin/**`、`plus-ui/src/router/modules/reader-admin.ts`
- 小程序/H5：`reader-uniapp/src/**`
- 数据库脚本：`script/sql/ry_reader.sql`、`script/sql/upgrade/**`、阅读器相关初始化/升级脚本

## 强制要求
- 每个阅读器相关的 `Java`、`TypeScript`、`Vue` 核心文件都要有文件级注释，说明该文件负责的业务职责。
- 实体、BO、VO、TypeScript 接口等数据结构要补字段注释，至少说明字段含义或用途。
- `private final` 依赖注入成员、关键常量、关键配置项也要补注释，至少说明该依赖在当前类里承担什么职责。
- Service、Controller、API 模块中的公开方法要补方法注释；复杂私有方法要补核心流程注释。
- `Cache`、`Parser`、`Job`、`Utils`、`Vue` 页面中的核心函数同样要补方法注释，不能因为方法短就省略。
- 每个复杂业务流程都要有关键逻辑注释，至少覆盖：
  - 文件导入与解析
  - 作品上架/下架状态联动
  - 管理端目录与章节预览
  - 小程序/H5 阅读跳转
  - 阅读进度同步与恢复
- 方法内部出现以下情况时，必须补流程注释：
  - 状态流转
  - 条件分支的业务原因
  - 批量查询后再映射
  - 缓存读写/失效
  - 幂等处理
  - 回退/兜底逻辑
  - 跨端兼容处理
- 注释要解释“为什么这样做”或“这一段在业务链路里的作用”，不要写逐行翻译式废话。
- JSON 配置文件如果语法不允许注释，不要强行写注释，应把说明放在相邻代码、文档或 `AGENTS.md` 里。
- 所有阅读器新增数据库表必须补齐表注释与字段注释；新增字段、状态字段、定位字段、时间字段也不能省略注释。
- 所有阅读器升级 SQL 在修改表结构时，如果涉及新表、新字段或字段语义变化，必须同步维护注释，不能只改类型不改说明。

## 分层规范
- 类注释：
  - 必须说明文件职责、适用场景、所在链路位置。
- 字段注释：
  - 适用于实体、BO、VO、DTO、TypeScript interface/type、页面核心状态。
  - 必须说明字段含义、用途，必要时说明单位、状态枚举或来源。
- 依赖注入/常量注释：
  - 适用于 Java/Spring 的 `private final` 成员、`private static final` 常量、前端脚本中的关键依赖配置。
  - 必须说明该依赖或常量为什么存在、服务哪段业务链路，而不只是重复变量名。
- 公开方法注释：
  - 必须写在所有 `public` 方法上，说明输入/输出意图和业务动作。
- 私有方法注释：
  - 只要方法承担转换、校验、构造、查询条件拼装、缓存操作、容错处理等职责，就必须补注释。
- 方法体内关键流程注释：
  - 不是每行都注释，但所有“看不注释就不容易秒懂”的关键逻辑都必须补。
- 引入文件注释：
  - `API`、`Router`、`Type`、`Utils`、`Cache`、`Parser`、`Job`、`Page`、`Component` 这些文件都必须有文件级注释。
  - 当一个文件存在多组非直观 import 或跨模块依赖时，应补“依赖分组说明”注释，解释请求工具、共享类型、平台能力、第三方 SDK 等引入原因。
- SQL DDL 注释：
  - 每张业务表都必须有表注释，说明该表在阅读器链路中的职责。
  - 每个字段都必须有字段注释，至少说明业务含义、单位、状态枚举、引用关系或使用场景。
  - 状态字段要明确状态值含义；布尔/开关字段要明确取值语义；时间字段要明确记录的是创建、发生还是同步时间。
  - 升级脚本中的 `ALTER TABLE`、`MODIFY COLUMN`、`ADD COLUMN` 也要同步携带注释，避免新库和旧库元数据不一致。

## 推荐粒度
- Controller/Page：说明页面或接口入口承接的业务场景。
- Service：说明状态流转、缓存策略、兼容逻辑、兜底策略。
- API/Utils：说明参数约定、跨端差异、复用原因。
- 依赖声明区：说明注入成员、请求工具、共享类型、平台能力各自承担的职责。
- Cache：说明缓存键、脏标记、回刷策略、失效策略。
- Parser：说明支持格式、解析入口、当前实现边界。
- 阅读页：说明章节恢复、进度回填、继续阅读、小说/漫画差异点。

## 提交前自检
- 这次改动涉及的阅读器文件，是否都能在 30 秒内看懂职责。
- 这次改动涉及的核心流程，是否至少有 1 处注释解释关键设计意图。
- 这次改动里的每个新增 `public` 方法，是否都补了方法注释。
- 这次改动里的数据结构字段，是否都补了字段注释。
- 是否出现了会破坏语法的注释写法，尤其是 JSON、配置文件、脚本声明文件。
- 这次改动涉及的 SQL 脚本，是否已经补齐表注释、字段注释以及升级脚本中的注释同步。

## 执行约定
后续继续开发阅读器需求时，把“补注释”视为与“写接口”“补页面”“跑通联调”同级的完成条件，不单独排到最后处理。
